# Internationalization (PT + EN)

Biblioteca: **next-intl v4** com roteamento por prefixo. PT em `/`, EN em `/en`
(`localePrefix: "as-needed"` — o idioma padrão não leva prefixo).

## Infra

- `i18n/routing.ts` — locales `["pt","en"]`, default `pt`, prefix `as-needed`.
- `i18n/request.ts` — `getRequestConfig` carrega `messages/<locale>.json`.
- `i18n/navigation.ts` — `Link`, `redirect`, `usePathname`, `useRouter` locale-aware.
- `proxy.ts` — middleware do next-intl (Next 16 renomeou `middleware` → `proxy`).
- `next.config.ts` — envolvido por `createNextIntlPlugin()`.
- `messages/pt.json` + `messages/en.json` — todas as strings da landing.

## Estrutura de rotas

Tudo movido para `app/[locale]/` (layout, landing, login, painel, admin). O layout
`[locale]/layout.tsx` define `<html lang={locale}>`, `NextIntlClientProvider`,
`generateStaticParams` (pt/en) e `generateMetadata` traduzida. Cada página chama
`setRequestLocale(locale)` → a landing é **SSG para `/pt` e `/en`**.

## Auth locale-aware

- Actions movidas para `lib/auth/actions.ts`.
- `logout(locale)` e os redirects de login/painel/admin usam o `redirect` do next-intl
  com o locale atual, então o usuário permanece no idioma escolhido.
- `Sidebar`/`PanelPlaceholder` passam o locale (via `useLocale()` / prop) ao `logout`.

## Tradução da landing

Todos os componentes usam `useTranslations`:
Hero (inclui card do mascote), Marquee, Categories, Benefits, HowItWorks, Ranking
(placeholders, dias da semana, aberto/fechado, pedidos), Footer, LeadModal, metadata.
Rich text (`t.rich`) para trechos com `<b>` (subtítulos do hero e do ranking).
Dados não-textuais (imagens, ícones, nomes de estabelecimentos, cidades, culinárias)
permanecem em código — só o "chrome" de UI é traduzido.

## Seletor de idioma

`components/site/LanguageSwitcher.tsx` — pill fixo no canto superior direito (PT | EN).
Troca via `router.replace(pathname, { locale })`, preservando a rota atual.

## Escopo

Landing, **Login**, **Painel do Estabelecimento** e **Painel Admin** 100% traduzidos (PT + EN).

### Painel Admin (3ª etapa)

- Namespace `admin` (sidebar, period, dashboard, faturamento, buscas, cadastros, status,
  taxas, backlog, editor, confirm, tipo, plan, method).
- **Tipos de estabelecimento** e **planos** traduzidos por mapa (`admin.tipo.<nome>`,
  `admin.plan.<nome>`) — aplicados em Dashboard (por tipo), Cadastros, editor e Buscas (card de tipo).
- **Meses** locale-aware: `monthOptions(now, locale)` formata "Julho de 2026" / "July 2026".
- Confirmação de exclusão traduzida via `AdminApp` (reusa `ConfirmDialog`).
- Plurais ICU (estabs., transações/compras, buscas). Conteúdo do tenant (nomes, cidades,
  itens, cartões) permanece em PT.

### Login + Painel (2ª etapa)

- Namespaces `auth`, `login` e `panel` (com sub-objetos: sidebar, bell, realtime,
  status, toasts, pedidos, cardapio, editor, confirm, qr, kpis, audit, perfil, config,
  cat, sub, pay, payShort, placeholder).
- **Erro de login** vira um código (`invalidCredentials`) que o LoginScreen traduz.
- **Toasts / mensagens de senha e impressora** ficam no `PanelApp` e usam `t(...)`.
- **Refactors:** `TABS` guarda só `[id, ícone]` (labels via `nav.<id>`); `statusBadge`
  virou `statusColors` (cores) + label traduzido por `panel.status.<st>`.
- **Taxonomia** (categorias/subcategorias) e **métodos de pagamento** traduzidos por
  mapa (`panel.cat.<nome>`, `panel.sub.<nome>`, `panel.pay.<id>`).
- **Conteúdo do estabelecimento** (nomes de itens, descrições, locais dos pedidos,
  nomes de clientes) **permanece em PT** — é dado do tenant, não UI.
- Plurais via ICU (`{count, plural, ...}`) em contagens (itens, transações, pgtos).
- Placeholder do admin é translation-driven (`panel.placeholder.admin.*`).

## Verificação

`/` → lang=pt, título PT · `/en` → lang=en, título "Your digital waiter" · seletor
troca idioma preservando a rota · `/en/painel` autenticado renderiza com lang=en ·
`npm run build` (landing SSG pt+en) + `npm run lint` limpos.
